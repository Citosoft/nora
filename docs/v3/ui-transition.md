# Adapting Nora's interface to v3

Updated 2026-11-09 after the owner's clarification. This is a source-backed migration map for the **whole interface**, not permission to replace Nora's shell or to leave v2 workflows attached to a new chat pane. It supplements [the screen specification](ui-specification.md), [the execution audit](audit.md) and D44–D45 in [the decision record](ui-discovery.md).

## Product model

**Thread** is the primary user-facing unit: a persistent conversation with a provider, workspace/environment, queued instructions, execution history and review evidence. Starting an agent and starting a thread become the same product action. There must not be separate active Agents, Threads and API Chat systems representing the same work.

An agent runtime is the execution provider behind a thread. A provider-native subagent is activity inside its parent thread unless the provider exposes independently navigable detail. A Nora-created child thread has its own identity and a parent link. A workflow coordinates linked threads. A manual terminal remains an independent shell.

Use thread terminology consistently in navigation, buttons, tabs, menus, shortcuts, empty states, search, settings and notifications. The internal conversation contracts can retain their domain names. Historical records retain their original provenance; do not relabel terminal logs as native conversations.

## Primary flow: New thread

Every ordinary creation entry point opens the **New thread screen in the existing center region**. The same draft can occupy a tab or saved grid pane. It is the chat view before its first message, not a separate configuration wizard.

The screen contains a focused prompt composer, a compact provider/model selector and workspace/environment/branch selection. Inherit sensible defaults and make them easy to inspect or change. Personal workspaces have no branch control. Show real branches/worktrees from the owning host; never treat a display label or arbitrary renderer path as execution authority.

Advanced permissions, reasoning, supported skills and checkout/worktree options use concise contextual controls. Do not port command overrides, resume commands, initial-prompt delivery modes, generated names and launch/trust steps into another large form. A title can be derived after submission. Credentials and installation belong in provider settings; readiness errors preserve the draft and link to the relevant setup action.

First send creates the durable thread and native execution. Before that, choosing a provider/model does not launch an agent. Workspace/branch admission must finish before execution. Changing branch must not silently move an existing thread or checkout underneath running work. Real writer/dirty-checkout conflicts receive contextual resolution, including an isolated worktree where supported.

Task/spec/review/browser/editor actions open this same screen with a reviewable instruction and context already filled. Distinguish **open a draft** from **send to an existing thread**. A deliberate workflow Run action may start its configured linked threads without showing an interactive draft for every step; it uses the same backend commands and evidence.

## Chat design contract

Use Claude Desktop and ChatGPT Desktop as interaction-quality references: a clear writing surface, restrained controls, comfortable reading and continuity between an empty thread and an ongoing conversation. These references guide the experience inside Nora's adapted workbench; this document does not claim new visual research on their current versions.

- **Empty thread:** calm heading and a centered, generous composer. At most a few relevant role-shaped starters, visually secondary to writing. Avoid dashboards, dense form rows and competing setup cards.
- **Model picker:** one trigger opens a two-column popover, with provider icons on the left and native model choices on the right (D46). Browsing a provider does not commit; choosing a model does. Reuse existing product icons and the Radix popover; support loading/empty/error/auth and keyboard dismissal/focus.
- **Composer:** one coherent surface; clear Send/Queue/Interrupt affordances; compact selectors and contextual menus; growing text area, labeled context chips and predictable keyboard/IME behavior. Supported options remain discoverable without displaying every setting permanently.
- **Ongoing thread:** the same composer moves to the lower edge of the pane; a restrained header identifies the thread and execution context. Keep the reading column centered, using the existing fonts/themes and v3 sizing baseline. Preserve draft text and focus through layout changes.
- **Transcript:** well-spaced Markdown, readable code and lists, copy actions, compact tool groups and provider reasoning collapsed by default. Failures expand meaningfully; normal activity does not become a wall of logs. Streaming remains stable and respects a user who scrolls away.
- **Requests and queues:** approvals/questions appear adjacent to the composer with the provider's real choices. Unsent queued instructions are editable/removable; accepted, running, completed and unconfirmed states are visually distinct. Expose no terminal trust-prompt automation.
- **Results:** responses remain the focus. Changes, files, validation and provenance are linked to real evidence in Nora's supporting panes. Do not show fabricated completion or validation badges.
- **Polish:** keyboard-first interactions, clear focus restoration, narrow-pane layouts, quiet reduced-motion-aware transitions, good empty/loading/error states and light/dark parity are acceptance requirements, not a later cosmetic pass.

These are concrete design requirements. The exact screen composition still needs review in the context of Nora's actual shell; the earlier detached generic-shell mockup is not the implementation template.

## Implementation sequence and completion gates

1. **Agree the adapted screen map and thread pane.** Review New thread and ongoing-thread composition in Nora's current chrome/sidebar/tab/panel context. A thread-pane mock does not approve a separate app shell.
2. **Complete thread navigation and view contracts.** Define workspace thread summaries, active/attention views, tab/pane identities and saved-layout migration. These contracts must cover every affected region before production wiring.
3. **Build the polished thread experience.** New/ongoing states, selectors, composer/context, timeline, requests/queues and evidence, including loading/error/narrow/keyboard behavior. Existing tools stay reachable.
4. **Migrate creation and handoff entry points as one coherent delivery.** Dialog/toolbar/sidebar/shortcut/task/spec/note/browser/editor/forge actions share the new-thread draft or explicit thread-send path. Workflow automation shares the same durable execution commands.
5. **Complete migration, activation and removal.** Replace production managed/API/loop execution callers together; preserve histories/layouts/preferences; remove superseded execution controls and IPC. This is the v3 replacement on this branch, with no v2 runtime switch.
6. **Review the actual integrated app.** Confirm no duplicate agent/thread/chat concept, dead buttons, lost tools or shell regression; run native/remote/recovery and visual acceptance. Claude's usage constraint still limits authenticated testing.

The first implementation cutover must not leave visible old buttons calling removed IPC. Conversely, retaining the shell must not leave its managed-terminal or renderer-AI execution running behind the new thread UI. The surface map above is the checklist for that complete replacement.

### Prepared thread-region boundary

[ThreadWorkspaceComposition](../../renderer/components/app/views/ThreadWorkspaceComposition.tsx) now provides typed native navigation, tabs and center ports without rendering shell chrome. The prepared [ThreadNavigation](../../renderer/components/app/panels/threads/ThreadNavigation.tsx), [ThreadTabs](../../renderer/components/app/panels/threads/ThreadTabs.tsx) and [ThreadViewContent](../../renderer/components/app/panels/threads/ThreadViewContent.tsx) use one [presentation store](../../renderer/components/app/logic/thread-workspace/store.ts) for retained drafts and view references. Native execution and transcript state stay with the host. Per-view draft persistence replaces the preliminary single global pending instruction. These components have fixture-based Electron acceptance; they are not yet mounted in the production shell.

The next delivery must migrate the live shell's mixed tool tabs/grid references, all creation/context/handoff callers and their persistence, then activate the native gateway and remove superseded managed/API execution together. Registered-checkout selection is implemented; new branch/checkout provisioning and legacy saved-layout migration remain outstanding. This boundary preserves working old production callers until their replacement is complete, without introducing a compatibility adapter or two live runtimes.
