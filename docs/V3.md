# Nora v3: Native Agent Interface & Orchestration Rewrite

**Project:** Nora Desktop  
**Version:** 3.0  
**Scope:** Major architectural and user-interface redesign  
**Technical reference:** https://github.com/pingdotgg/t3code  
**UI references:** T3 Code and OpenAI Codex Desktop

## 1. Executive summary

Nora v3 will fundamentally change how users interact with AI coding agents.

The existing architecture launches agents such as Claude Code and Codex in embedded terminal sessions. This terminal-first approach will be replaced by a fully custom, provider-agnostic React chat interface, supported by structured provider adapters, a central orchestration engine and persistent execution state.

Nora will communicate with underlying coding-agent runtimes through their supported SDKs and structured protocols.

Embedded terminals will remain available for manual CLI use, but will no longer be the default mechanism for interacting with coding agents.

**This is a major rewrite. Existing terminal-dependent architecture may be removed and rebuilt where necessary. Internal backwards compatibility with v2 is not a requirement.**

However, Nora's existing functionality, especially multi-agent orchestration, cross-agent context sharing, Git integration, project management and remote execution, must be preserved or improved.

The implementation must also include a substantial UI redesign, guided by detailed consultation with the product owner.

## 2. Mandatory requirement: UI discovery and consultation

**CRITICAL: The implementing agent MUST conduct a detailed, interactive UI discovery process with the product owner before designing or implementing substantial frontend changes.**

The architectural direction described in this specification is already decided. However, the final UI layout, navigation, interaction patterns, visual presentation and feature placement are NOT decided.

The agent must not independently make major UI design decisions based solely on assumptions, existing Nora layouts or reference applications.

### Required consultation process

Before implementing the new frontend, the agent must:

1. Audit Nora's existing interface, including its project navigation, tabs, panels, terminal layouts, session management and settings.
2. Examine T3 Code's actual React frontend implementation and available interface references.
3. Examine the Codex desktop application's UI and interaction patterns through available documentation, screenshots and product references.
4. Identify which existing Nora UI components and workflows should be retained, redesigned or removed.
5. Present the product owner with a detailed breakdown of the proposed UI changes.
6. Ask specific questions about the layout and user experience, offering sensible recommendations and explaining tradeoffs.
7. Gather decisions iteratively, using follow-up questions where necessary.
8. Produce a written UI design specification reflecting the agreed decisions.
9. Obtain explicit approval before proceeding with substantial frontend implementation.

**Do not treat a lack of objection as approval.**

### How questions should be asked

Questions must be specific and grounded in actual interface designs.

Avoid vague questions such as:

- "How should the UI look?"
- "Do you prefer T3 or Codex?"
- "Should I modernise the sidebar?"

Instead, explain concrete alternatives.

For example:

"Codex organises conversations under projects in a persistent sidebar, while T3 Code separates chat content, context controls and supporting workspace tools. Nora currently uses terminal-oriented layouts. Would you prefer to retain Nora's existing project navigation and replace only the session content, or introduce a new project-and-thread navigation structure?"

The agent should explain its recommendation, the implications of each option and any relevant impact on Nora's existing features.

Ask questions in manageable groups, organised by design area. Do not present dozens of unrelated decisions simultaneously.

The agent should be proactive in recommending good UX solutions rather than simply asking the owner to design the product.

### Mandatory topics for consultation

**A. Overall application layout**

Discuss:
- Whether the existing Nora sidebar remains.
- Whether navigation should be project-first, agent-first or conversation-first.
- How conversations should be grouped and sorted.
- Whether multiple conversations can remain open in tabs.
- Whether users can view multiple conversations simultaneously.
- How existing multi-pane and split-view functionality should work.
- Where global navigation and application settings should live.
- How inactive, completed and running conversations are distinguished.

**B. Main chat experience**

Discuss:
- Message alignment, spacing, typography and content width.
- How streaming responses appear.
- Whether thinking and reasoning are visible, collapsed or configurable.
- How tool calls should be grouped or expanded.
- Whether command output appears inline or in a separate pane.
- How agent progress is communicated.
- How long-running sessions are presented.
- Whether conversation timelines include task milestones.
- How errors, interruptions and retries appear.

**C. Message composer**

Discuss:
- Composer position, dimensions and appearance.
- Provider and model selection placement.
- Reasoning-effort and permission controls.
- File attachments, screenshots and drag-and-drop.
- Project-file mentions and contextual references.
- Skill selection and slash commands.
- Enter-to-send and keyboard shortcuts.
- Queued messages and editing.
- Stop, interrupt and resume controls.
- Whether settings belong inside or outside the composer.

**D. Tool calls and permissions**

Discuss:
- Compact versus expanded execution cards.
- Whether multiple related tool calls should be grouped.
- Inline approval buttons versus modal dialogs.
- File-edit summaries.
- Command output previews.
- Failed tool calls and retry actions.
- The presentation of sensitive permissions.

**E. Agent management**

Discuss:
- How users create agents or conversations.
- How parallel agents are displayed.
- Whether subagents appear inside parent conversations or as separate sessions.
- How goals, loops and tasks are visualised.
- Cross-agent communication and handoffs.
- Agent status indicators.
- Notifications for agents requiring attention.

**F. Git and development tools**

Discuss:
- Whether diffs open inline, in drawers, tabs or side panels.
- How modified files are listed.
- How Git branches and worktrees are selected.
- Placement of PR review features.
- Whether file editing remains alongside chat.
- How the terminal is opened from a conversation.

**G. Visual identity**

Discuss:
- Light and dark themes.
- Existing Nora branding.
- Typography and spacing.
- Compact versus spacious layouts.
- Icons, status indicators and visual hierarchy.
- Animation and streaming behaviour.
- Resizable panels and responsive layouts.

### UI consultation deliverables

Before frontend implementation, produce:

- Current UI audit.
- T3 Code and Codex UI comparison.
- Recommended Nora v3 information architecture.
- Screen-by-screen layout specification.
- Component inventory.
- Interaction and state diagrams.
- Explicit record of owner decisions.
- List of unresolved UI questions.
- Implementation plan.

Where practical, provide wireframes or visual mockups for review.

No substantial frontend implementation should begin until the proposed interface has been approved.

Backend architectural analysis, technical investigation and isolated proof-of-concept work may proceed before UI approval.

## 3. UI reference: T3 Code

**Repository:** https://github.com/pingdotgg/t3code

T3 Code is a particularly relevant reference because it provides a custom interface around multiple coding agents through provider adapters and a shared orchestration system.

The implementing agent must examine the actual T3 Code source, rather than relying solely on this description.

### 3.1 Overall interface approach

T3 Code uses a conversation-centred workspace.

Its interface separates the responsibilities of:

- Navigating projects and conversations.
- Viewing the current conversation.
- Composing instructions.
- Displaying agent execution.
- Managing provider settings.
- Inspecting workspace files and diffs.
- Accessing terminals and supporting tools.

The UI is independent of the terminal interfaces exposed by underlying providers.

**Application to Nora:** Use this as a reference for moving agent interaction out of terminals while retaining rich development tooling around the conversation.

The product owner must decide which parts of Nora's existing multi-pane experience remain.

### 3.2 Chat timeline

T3 Code's frontend provides specialised components for presenting structured agent activity.

Instead of rendering a continuous terminal transcript, the interface can distinguish:

- User messages.
- Assistant responses.
- Streaming message content.
- Reasoning or thinking activity.
- Tool execution.
- File changes.
- Approval requests.
- Plans and progress.
- Subagent activity.
- Failures and interruptions.

These different event types can receive distinct presentation components.

**Potential Nora approach:**

Display user and assistant messages prominently while making tool execution visually secondary.

For example, a series of filesystem reads or shell commands could appear as compact activity rows, expandable when the user wants detailed output.

The agent must ask whether Nora should show all tool activity by default or favour a cleaner, collapsed interface.

### 3.3 Structured tool activity

T3 Code has dedicated UI components for command output, tool activity and approval handling.

Relevant components include:

- `CommandOutputPanel.tsx`
- `ComposerPendingApprovalPanel.tsx`
- `ComposerPendingUserInputPanel.tsx`
- `ChangedFilesTree.tsx`

This separation enables richer presentation than raw terminal output.

**Potential Nora approach:**

A tool operation might appear as:

"Running tests"  
`npm test`  
Status: Running

After completion, the row could display success or failure, elapsed time and an option to expand the complete output.

For file edits, show the affected filename and a diff action rather than dumping the entire patch directly into the chat.

This is a proposed presentation pattern, not a requirement to copy T3's exact appearance.

### 3.4 Message composer

T3 Code implements a dedicated React composer with supporting controls for contextual input.

Relevant files include:

- `ChatComposer.tsx`
- `ComposerFooterControls.tsx`
- `ComposerAttachmentStrip.tsx`
- `ComposerCommandMenu.tsx`
- `ContextWindowMeter.tsx`

The composer is a functional part of the agent experience, not simply a text input.

**Potential Nora approach:**

Design a unified composer supporting provider selection, model choice, reasoning settings, permission mode, attachments, file references and task instructions.

Discuss whether advanced controls should be visible at all times or progressively disclosed.

The composer must remain usable when the window is narrow or multiple chats are displayed side by side.

### 3.5 Approvals and questions

T3 Code converts native provider permission requests and questions into structured UI interactions.

Examples include command approvals, filesystem permissions and questions requiring user input.

The interface can present actions directly in the conversation rather than forcing users to interact with terminal prompts.

**Potential Nora approach:**

When an agent requests permission to run a command, display a clearly defined card containing the command, relevant scope and the actual options supported by that provider.

The user should be able to respond without leaving the chat.

Permissions must be handled by provider-native enforcement. Nora must not imply it can grant or restrict permissions that the underlying provider does not support.

### 3.6 Chat and workspace layout

T3 Code provides separate components for chat layout, contextual panels and supporting surfaces.

Relevant files include:

- `ChatView.tsx`
- `ChatCanvas.tsx`
- `ChatRightPanel.tsx`
- `ChatHeader.tsx`
- `ChatMarkdown.tsx`

This provides a useful reference for keeping conversation rendering separate from workspace layout.

**Potential Nora approach:**

Allow chat to coexist with a file viewer, Git diff, terminal, browser preview or another agent conversation.

Whether these appear as tabs, drawers, split panes or persistent columns must be decided through UI consultation.

### 3.7 Lessons for Nora

The most important lessons are:

1. Build a shared conversation renderer rather than provider-specific chat screens.
2. Model tools and permissions as structured interactions.
3. Keep provider configuration separate from ordinary chat rendering.
4. Support conversation persistence and reconstruction independently of UI state.
5. Use composition and specialised components to avoid an oversized, monolithic chat component.
6. Preserve access to powerful development tools without allowing them to dominate the chat experience.

T3 should be treated as an architectural and UX reference, not a design that Nora must duplicate.

## 4. UI reference: OpenAI Codex Desktop

**Official reference:** https://openai.com/index/introducing-the-codex-app/

Codex Desktop provides a second important reference: a desktop-native experience organised around agent work, rather than terminal interaction.

The implementing agent must review the current product UI through available screenshots, official documentation and relevant public examples before finalising Nora's design.

The patterns below describe documented Codex concepts and recommended areas for Nora to evaluate. They are not a claim that every layout element is identical in every Codex release.

### 4.1 Project-oriented navigation

Codex organises agent threads around projects.

A user can select a project, view associated work and switch between conversations without manually managing CLI processes.

This creates a distinction between the project being worked on and the conversation performing the work.

**Potential Nora approach:**

A left sidebar could contain projects, with expandable conversations under each.

Example:

Nora
- Project Alpha
  - Implement authentication
  - Fix database migration
  - Review pull request
- Project Beta
  - Investigate performance
  - Add new API endpoint

Each conversation could display its associated provider and execution status.

This is an illustrative proposed layout, not a literal Codex screenshot.

The agent must ask whether existing Nora navigation should be adapted or replaced.

### 4.2 Central conversation workspace

Codex presents coding tasks as conversations with individual agents.

The workspace focuses on the active task, presenting instructions, agent activity, results and related changes.

The UI is designed for interacting with an agent over multiple turns rather than supervising a terminal command.

**Potential Nora approach:**

Make the conversation the primary content area.

Use a clear visual hierarchy where human messages and meaningful agent responses are prominent, while tool activity, command output and intermediate execution details can be expanded when needed.

The implementing agent must ask how much execution detail the owner wants visible by default.

### 4.3 Parallel conversations and agents

Codex supports concurrent threads within projects.

Users can switch between tasks while agents continue working independently.

Codex also supports Git worktrees to isolate changes from parallel work.

**Potential Nora approach:**

Preserve Nora's existing strengths in concurrent execution, but give users clearer visual status and navigation.

A session list could show:

- Running.
- Waiting for approval.
- Waiting for user input.
- Completed.
- Failed or interrupted.

Where agents operate on the same repository, Nora should offer appropriate workspace isolation.

The agent must ask whether Nora should emphasise a project-first thread list, multi-agent dashboard or split-screen layout.

### 4.4 Integrated code review

Codex allows users to review changes associated with a thread, comment on diffs and open files in an editor.

This connects the conversation directly to its effects on the codebase.

**Potential Nora approach:**

Add a prominent changed-files summary for agent work.

Allow the user to open a diff from the conversation, inspect modifications and provide follow-up instructions based on selected changes.

Consider whether the diff should appear:

- In a right-hand review panel.
- As a separate tab.
- In a split view alongside chat.
- As an inline expandable section.

The implementing agent must present alternatives and get an explicit decision.

### 4.5 Execution environment selection

Codex supports different execution contexts, including local work and isolated worktrees, with cloud execution available in supported workflows.

This distinction lets users control where an agent operates.

**Potential Nora approach:**

Expose the selected project, workspace and execution environment clearly.

Nora must continue supporting local and SSH-based projects.

Avoid forcing environment details into every message. Place controls where users can find them without cluttering ordinary conversations.

### 4.6 Task outcomes and review

Codex's experience is oriented around delegating work and returning to inspect the result.

Its automation functionality also uses review-oriented workflows so completed work can be examined before further action.

**Potential Nora approach:**

On completion, present a concise result summary covering:

- What was changed.
- Files affected.
- Tests executed.
- Any errors or unresolved issues.
- Suggested next actions.
- Links to review the diff or continue the conversation.

Nora's existing goals and loops could extend this into more advanced execution and review workflows.

The agent should ask how task results and completed agents should be presented.

### 4.7 Composer and contextual controls

Codex uses a dedicated task composer within its desktop workflow, with project and execution settings connected to task creation.

Nora should evaluate a similar approach where model, execution mode, context and permissions can be chosen without manually interacting with a CLI.

The agent must investigate the current Codex composer and compare its controls with T3 Code.

Specifically, discuss whether Nora should have:

- A minimal composer with secondary controls.
- A feature-rich composer exposing key options.
- Configurable compact and advanced modes.

No choice should be made without product-owner consultation.

### 4.8 Lessons for Nora

Codex Desktop demonstrates the value of:

1. Project-oriented organisation.
2. Persistent, resumable task conversations.
3. Parallel agent execution.
4. Integrated code review.
5. Workspace isolation.
6. Clear distinctions between execution environments.
7. A focused task-oriented interface rather than an embedded terminal experience.

These patterns should inform the Nora v3 redesign without replacing Nora's own identity or differentiating capabilities.

## 6. New technical architecture

The v3 architecture will have four primary layers.

### 6.1 Custom React interface

Responsible for:

- Conversation navigation.
- Message rendering.
- Streaming display.
- Tool and reasoning presentation.
- Approvals and questions.
- Agent and task management.
- Workspace and Git integration.
- Multi-pane layouts.

The frontend must not communicate directly with individual coding-agent CLIs.

### 6.2 Client runtime and event transport

Responsible for:

- Typed commands.
- Subscriptions.
- Event updates.
- State hydration.
- Reconnection.
- Optimistic UI where safe.
- Cancellation and error handling.

This layer should be independent of the underlying provider.

### 6.3 Central orchestration engine

Responsible for:

- Session lifecycle.
- Agent execution.
- Concurrent workflows.
- Task scheduling.
- Goals and loops.
- Cross-agent collaboration.
- Context handoffs.
- Permissions and questions.
- Persistent state.
- Failure recovery.
- Background execution.

Execution must not depend on an active UI component or an open terminal.

### 6.4 Provider adapters

Each provider adapter translates between Nora's shared contracts and the provider's native runtime.

Initial integrations:

**Claude Code**

Use `@anthropic-ai/claude-agent-sdk`.

Support native session management, streaming, tools, permissions, models, skills and other available provider functionality.

**Codex**

Use the Codex App Server protocol.

Support native threads, turns, structured events, tools, approvals, interruption, session continuation and available model controls.

**Other agents**

Create a scalable adapter mechanism for Gemini, OpenCode and future providers.

Prefer supported SDKs, ACP or other structured application protocols.

No managed-agent workflow should rely on scraping terminal output as its primary integration method.

## 7. Shared provider contract

Introduce a strongly typed provider adapter abstraction supporting:

- Installation and readiness checks.
- Authentication status.
- Provider instances and configurations.
- Model discovery.
- Capability declarations.
- Session creation and continuation.
- Message submission and attachments.
- Structured event streaming.
- Tool execution updates.
- Permission and input requests.
- Interruption and termination.
- Context and token usage.
- Provider failures and usage limits.
- Native conversation history where available.
- Session cleanup and recovery.

The orchestration engine must depend on this abstraction rather than provider-specific implementation details.

Each adapter should advertise its supported capabilities.

Unsupported actions must be hidden, disabled or handled through explicitly documented alternatives.

Do not assume native conversations can be transferred between different providers.

## 8. Orchestration and multi-agent capabilities

Nora's existing multi-agent functionality must be preserved and integrated with the new execution model.

Requirements include:

- Multiple concurrent agents across providers.
- Task dependencies and scheduling.
- Sequential and parallel agent execution.
- Goal and loop management.
- Context sharing across sessions.
- Provider-independent handoffs.
- Subagent visibility.
- Execution history.
- Retry and recovery behaviour.
- Workspace conflict protection.
- Structured agent status and progress.

Provider-native session state should be retained whenever possible.

When native cross-provider continuation is unavailable, Nora should generate a structured, portable context handoff.

The orchestration architecture must distinguish commands being accepted from actual provider execution completing.

---

## 9. Persistence and session lifecycle

Conversation state must be independent of terminal sessions.

Persist:

- Projects and workspaces.
- Provider configurations and instance references.
- Nora sessions and threads.
- Provider-native session identifiers.
- Messages and content.
- Execution events.
- Tool activity.
- Tasks and plans.
- Agent relationships.
- Approvals and questions.
- Context handoffs.
- Failure and recovery state.

Support reconstruction after application restarts.

Handle disconnected providers, interrupted processes, incomplete execution and failed reconnects explicitly.

Do not store provider credentials in plaintext conversation data.

The process or remote environment owning the workspace must also own provider execution and relevant filesystem access.

---

## 10. Retaining terminals

Nora must retain embedded terminals as an independent feature.

Users must still be able to:

- Open shell terminals.
- Launch Claude Code or Codex manually.
- Run commands and development servers.
- Use terminal presets.
- Work with local or remote shells.
- Place terminals alongside chats, diffs and other panels.

However:

**Terminals must no longer serve as the underlying runtime or rendering mechanism for managed AI conversations.**

Manual CLI sessions should not automatically appear as managed agent sessions unless a supported import or attachment mechanism is explicitly invoked.

---

## 11. Git and development workflow integration

Preserve:

- Git status and branches.
- File editing.
- Diff viewing.
- PR and MR review.
- GitHub integration.
- Worktree support.
- Browser previews.
- SSH-based projects.
- Project files and navigation.

Improve integration with structured agent activity.

Users should be able to inspect files changed by an agent directly from its conversation.

Where rollback is supported, ensure filesystem restoration and provider conversation restoration are handled according to actual provider capabilities.

---

## 12. Legacy architecture removal

The implementing agent must audit the existing terminal-first implementation and identify obsolete systems.

Potential removal targets include:

- Terminal-based agent launch orchestration.
- CLI output parsing.
- Prompt submission through terminal input.
- Terminal-based session state detection.
- Terminal-dependent execution tracking.
- Terminal-specific agent UI components.
- Legacy orchestration built around shell processes.

Do not preserve these systems simply because rewriting them requires substantial work.

Retain reusable terminal infrastructure for manual shell use.

Preserve user settings, project data and existing session records through an explicit migration or archival strategy.

Do not silently delete user data.

A clean architecture is preferred over maintaining two competing systems indefinitely.

## 14. Acceptance criteria

Nora v3 is complete when:

1. Claude Code and Codex run through Nora's custom chat interface without requiring embedded terminals.
2. The frontend uses structured provider events rather than CLI output parsing.
3. The orchestration engine manages execution independently of the UI.
4. Provider adapters expose native capabilities consistently.
5. Multiple agents can work concurrently.
6. Cross-provider context sharing continues to function.
7. Nora's task, goal and loop capabilities are integrated with the new architecture.
8. Sessions and history persist correctly.
9. Existing project, Git, remote and development tools remain operational.
10. Embedded terminals are available independently.
11. Obsolete terminal-first execution architecture is removed.
12. The frontend follows an explicitly approved UI design.
13. All major UI decisions have been reviewed with the product owner.
14. The owner has had the opportunity to review the new experience before final UI sign-off.

## 16. Final implementation directive

**Nora v3 must become a native multi-agent development environment, not a terminal application wrapped around CLI processes.**

The implementing agent has permission to undertake substantial refactoring, replace architectural foundations and remove obsolete code to achieve this objective.

However, this authority does not extend to independently deciding the new interface design.

The agent must actively collaborate with the product owner on UI and UX decisions, using T3 Code and Codex Desktop as detailed references.

The agent is expected to recommend strong design solutions, explain technical and usability tradeoffs, and ask follow-up questions until the significant UI decisions are clear.

**The architecture should be decisively modernised. The interface should be collaboratively designed.**

Preserve Nora's existing strengths in parallel agents, context sharing, orchestration and developer tooling while delivering a cleaner, more capable native chat experience.
